## 2a. Веха P1: оптимизация горячего пути (23.10)

Исследование производительности показало, что узкое место — **не** структуры
данных, а путь «сокет → горутина → сокет»: профиль живого сервера под
нагрузкой — 48 % системные вызовы, 48 % планировщик Go, меньше 3 % собственная
логика. CPU на запрос: 10.0 µs против 4.4 µс у Redis.

Сделано в ветке `feat/p1-hot-path`:
- copy-on-write для строковых значений (закрыта гонка: `GET` отдавал буфер
  стора без копии, а `APPEND`/`SETRANGE` писали в него на месте);
- буфер записи сокета 4 → 64 КБ (батч ответов пайплайна — один `write()`);
- ноль аллокаций на команду: поиск команды по байтам клиента, переиспользование
  контекста и буфера аргументов, `resp.ReadCommand`, поиск ключа в сторе по
  байтам — 13 → 6 аллокаций и 552 → 136 B на команду;
- протухание по выборке ключей (как в Redis) вместо скана keyspace под
  эксклюзивным `Lock` — p99 0.575 → 0.383 мс;
- счётчики выровнены по cache line, путь ожидания не берёт глобальный мьютекс
  без ожидающих;
- флаг `--pprof <порт>` — профиль работающего сервера.

Итог: +6 % rps на одиночных командах, +9 % под пайплайном, под P=100
реализация стала быстрее настоящего Redis.

## 2b. Веха P2: путь персистентности (AOF) и I/O (23.10)

Исследование после P1 нашло узкие места вне горячего пути:

- **AOF писал один системный вызов на команду** — с включённым AOF пайплайн
  (P=100, SET) падал с 2.17 млн до 265k rps, тогда как Redis с AOF выдаёт
  1.01 млн. Теперь команда кодируется в общий буфер (без аллокации) и пишется
  в файл пачками: при переполнении буфера, по таймеру
  (`--aof-flush-interval`, по умолчанию 100 мс) и всегда при `always`.
  Буфер сбрасывается **до** отправки ответов — клиент не видит ответа на
  команду, которой ещё нет в журнале.
- **Буфер чтения 4 → 64 КБ** (+ флаги `--buf-read-size`/`--buf-write-size`):
  массовая загрузка пайплайном +43 %.
- **Разбор аргументов AOF без аллокаций** (сравнение по байтам).

Итог: AOF-пайплайн ×6.6 (1.74 млн rps — быстрее Redis), одиночные команды и
обычный пайплайн без регрессий.

## 2c. Веха P3: шардирование стора (23.10)

Mutex-профилирование в Go по умолчанию выключено, поэтому после P1 в это было
легко поверить, но не измерить. После включения `SetMutexProfileFraction` в
`--pprof` contention нашёлся: write-лок стора на пути `SET` — 1.09 с ожидания
на 12 с нагрузки (c=100), читатели на `RLock` не видны вовсе.

Сделано в ветке `feat/p3-sharding`:
- `Store` разбит на 16 независимо блокируемых шардов (fnv-1a по ключу,
  `internal/store/shard.go`); публичный API стора не менялся — сервер и
  persist не тронуты;
- многоключевые операции (`MGET`/`MSET`/`DEL`/`RENAME`/`SMOVE`/`ZUNIONSTORE`/
  `ListMove`/`ZPopAny`/…) захватывают шарды всех ключей в порядке возрастания
  индекса: дедлоки исключены, операция атомарна по затронутым ключам;
- WATCH-реестр и `usedBytes` — per-shard; шард выровнен на cache line;
- `ExpireCycle`/`EvictCycle` семплируют по шардам, eviction перепроверяет
  жертву под локом (семпл может состариться);
- итерации (`KEYS`, `INFO`, `ForEach` для SAVE/AOF-rewrite, `FLUSH`) идут по
  шардам последовательно — результат может чередоваться с записью, как в
  Redis; снапшот SAVE перестал быть мгновенно-глобальным;
- конкурентный стресс-тест и тест атомарности multi-key —
  `internal/store/shard_test.go`.

Итог: паритет сквозных rps (машина шумная), +9 % GET при случайных ключах
c=50, +3 % под пайплайном; регрессий в store-бенчмарках нет. Структурный
барьер «один write-лок на все записи» снят; горячий ключ по-прежнему
сериализуется на одном шарде — так же, как в однопоточном Redis.

## 2d. Веха P4: writev для крупных значений и курсор SCAN (23.10)

Последние точечные резервы после P3:

- **Крупные bulk-ответы** (GET/MGET значений ≥ буфера записи): payload больше
  не копируется в bufio-буфер — `resp.Writer.WriteBulkLarge` отправляет
  `{заголовок, payload, CRLF}` одним writev через `net.Buffers`. Мелкие ответы
  продолжают батчиться; порядок байт покрыт тестами.
- **Курсор SCAN** кодирует «шард × смещение»: за вызов сортируется 1/16
  keyspace вместо полного снапшота. Полный обход 1000 ключей ×2.9 быстрее,
  вдвое меньше памяти. COUNT — по-прежнему позиции всего keyspace; обход
  неподвижного keyspace — каждый ключ ровно один раз. Формат курсора
  непрозрачен для клиента (как в Redis), валидация мусорных курсоров — без
  ошибки, обход просто завершается/продолжается.

## 2f. Веха P5–P7 — обходы, счётчики, аллокации (26.10)

Разведка показала: в профиле живого сервера наш код занимает меньше 1 % CPU
(56 % syscall'ы, 31 % kqueue, 24 % планировщик). Значит, на одиночных командах
микро-оптимизация rps не двигает, и выигрыш лежит там, где команда не упирается
в сокет.

- **P5 — обходы коллекций по снимку** (`internal/store/scan.go`): `HSCAN`/
  `SSCAN`/`ZSCAN` больше не строят полный снапшот на каждый вызов; снимок
  строится один раз на версию коллекции и переиспользуется обходом. Обход хеша
  на 100k полей: 27 с → 70 мс (Redis 8.2: ~350 мс). Версия коллекции
  поднимается при добавлении и удалении поля/члена, у zset — при любом
  изменении (порядок зависит от счёта); значения полей читаются при сборке
  страницы, поэтому устаревшего значения не бывает.
- **P6 — счётчики без блокировок**: учёт памяти больше не берёт RLock шардов
  (было 256 lock/unlock на пишущую команду при `--maxmemory`), счётчики команд и
  изменений разложены по 16 слотам, имя последней команды клиента хранится в
  атомарном указателе, конфигурация slowlog — в атомиках (гонка с `CONFIG SET`
  устранена).
- **P7 — аллокации**: ответы с числами пишутся без аллокации, запись строки
  переиспользуется при перезаписи (буфер значения не меняется на месте).
  SET: 6 аллокаций/136 B → 5 аллокаций/24 B.
- Попутно исправлены три ошибки журнала AOF: 15 команд писались в журнал
  дважды, `GETEX` без опции срока убивал ключ на реплее, восемь команд не
  считались пишущими (мимо проверки maxmemory, без пробуждения заблокированных
  клиентов).

Что осталось из перформанса после P7: разрыв на одиночных командах (0.86–0.90×)
лечится только сменой I/O-модели на event loop — осознанно не берём. Следующие
содержательные вехи — фичевые: M22–M23 (репликация).

## 2g. Веха P8 — event loop: решение и первый шаг миграции (28.10)

Профиль живого сервера: наш код меньше 1 % CPU, остальное — syscall'ы,
kqueue и планировщик. Один из syscall'ов лишний: netpoller Go работает в
edge-triggered режиме, поэтому на каждый запрос приходится `read` → EAGAIN →
парковка горутины → `read`. Настоящий Redis использует level-triggered
epoll и обходится одним `read` без пробуждения горутины.

Измерение (прототип `cmd/eventloop-proto`: один и тот же разбор и одни и те
же команды, две модели ввода-вывода) и замер на самом сервере
(`--io-mode=loop`) дали одно и то же:

| | горутины | event loop |
|---|---:|---:|
| прототип, CPU на команду (c=50) | 9.65 мкс | **4.44 мкс (−54 %)** |
| сервер, CPU на команду (SET, c=50) | 14.0–15.3 мкс | **8.0–9.7 мкс (−37…43 %)** |
| сервер, rps (SET, c=50) | 69.5–76.4k | **92.4–112.8k (+33…48 %)** |

Под пайплайном разница почти исчезает (≈1 мкс на команду в обеих моделях):
там стоимость syscall'ов амортизируется по пачке команд.

**Решение: сетевой слой переписывать стоит** (критерий вехи — ≥25 % CPU на
команду — выполнен с запасом).

Сделано (первый шаг миграции):

- `internal/netloop` — поллер поверх kqueue (BSD/macOS) и epoll (Linux) в
  level-triggered режиме;
- `internal/resp` — `ParseCommand`, разбор команды из буфера (тест сверяет
  его с потоковым `ReadCommand`);
- `internal/server` — `--io-mode=loop`: тот же диспетчер команд, свой
  ввод-вывод; 8 из 9 сценариев сверки совпадают с Redis, отличается только
  `blocking.txt`.

Что осталось до полноценного режима:

1. **Блокирующие команды** (`BLPOP`, `BRPOP`, `BLMOVE`, `BZPOPMIN/MAX`,
   `XREAD BLOCK`): в цикле клиент должен уходить в список отложенных, а цикл
   — продолжать работать. Сейчас эти команды отвечают ошибкой.
2. **Pub/Sub**: насос подписчика должен писать в очередь, которую разбирает
   цикл, а цикл должен просыпаться для её отправки. Сейчас `SUBSCRIBE`
   отвечает ошибкой.
3. **Прочее**: `CLIENT LIST` в режиме loop, корректное закрытие соединений и
   клиентов, несколько циклов на ядра (SO_REUSEPORT) для CPU-тяжёлых команд,
   проверка порядка «команда в журнале → ответ клиенту» под AOF.

Пункты 1, 2 и 3 (кроме нескольких циклов) закрыты в вехе P9 — см. §2h.

Риски, о которых помнить: цикл не должен простаивать из-за долгой команды
(в Redis та же проблема, лечится I/O-потоками); при переносе нужно сохранить
инвариант copy-on-write стора и порядок записи в AOF.

## 2h. Веха P9 — полноценный режим event loop (28.10)

Веха P8 (PR #25) сделала только первый шаг миграции: цикл исполнял команды,
но не умел держать клиентов, которые ждут ключ, и не умел доставлять
сообщения подписчикам — такие команды отвечали ошибкой. Веха P9 закрыла
оба пробела; режим `--io-mode=loop` стал моделью ввода-вывода по умолчанию.

Сделано:

- **Блокирующие команды** в цикле (`BLPOP`, `BRPOP`, `BLMOVE`,
  `BZPOPMIN/MAX`, `XREAD … BLOCK`): клиент, которому нечего извлечь, уходит
  в список ожидания — аргументы команды копируются (буфер соединения
  переиспользуется), чтение соединения приостанавливается (как в Redis),
  команда выполняется снова, когда ключ становится доступен; по таймауту
  клиент получает null-массив. Поллер ждёт с дедлайном ближайшего
  заблокированного клиента, поэтому таймаут не будит весь сервер.
- **Pub/Sub** в цикле: насос-горутины нет — сообщения складываются в очередь
  соединения и пишутся циклом вместе с обычными ответами (порядок
  «подтверждение подписки → сообщение» сохраняется); переполненная очередь
  отключает медленного подписчика.
- **`internal/netloop`**: `Wait` с таймаутом (kevent/epoll_wait умеют его
  natively) и `Notify` — пробуждение поллера из другой горутины через
  socketpair; `PeerAddr` — адрес другого конца сокета (нужен для
  `CLIENT LIST` в режиме цикла, где у клиента нет `net.Conn`).
- **Исправлены дефекты цикла**: не обрабатывалось событие `Writable` (если
  сокет не принял ответ целиком, остаток не досылался никогда, а чтение
  уже было выключено — клиент вис); соединение, разорванное без ответа, не
  закрывалось (утечка дескриптора); `CLIENT REPLY OFF/SKIP` не
  поддерживался; `CLIENT LIST`/`CLIENT KILL` не видели клиентов цикла;
  `Server.Close()` не останавливал цикл — сервер не завершался по SIGTERM и
  крутился вхолостую.
- **`CLIENT UNBLOCK`**: заблокированный клиент отвечает ошибкой Redis
  (`ERR UNBLOCKED client unblocked via CLIENT UNBLOCK`) — раньше команда
  всегда отвечала «не заблокирован».
- **AOF**: блокирующие команды пишут в журнал эффект извлечения (`LPOP`,
  `RPOP`, `LMOVE`, `ZPOPMIN`), а не себя. Раньше `BLPOP` попадал в журнал
  как `BLPOP`, реплей его не знал: извлечённый элемент возвращался в
  список, а перемещённый терялся.
- **Сверка**: `scripts/compat-check.sh` поднимает три сервера — наш в
  горутинной модели, наш в режиме `--io-mode=loop` и настоящий Redis — и
  сравнивает сценарии с каждым. Все 9 сценариев совпадают в обоих режимах
  (в P8 расходился `blocking.txt`).
- **По умолчанию** `--io-mode=loop`; откат — `--io-mode=goroutine`.

Замеры (Mac M1, `redis-benchmark` 8.2.0, SET, n=2 000 000, c=50): 24.1–24.8
мкс CPU на команду и 55.5–57.6k rps у горутинной модели против
**9.9–10.0 мкс и 74.2–75.5k rps** у цикла (−60 % CPU, +29…35 % rps); под
пайплайном P=100 — 2.1–2.65 мкс против 0.50 мкс. Горячий путь цикла при
переходе с P8 на P9 не стал хуже (12.2–12.6 → 9.9–10.0 мкс). Подробности и
методика — в `BENCHMARKS.md` (раздел «Веха P9»).

Что осталось (следующая веха):

1. **Несколько циклов на ядра** (SO_REUSEPORT): очередь сообщений и список
   ожидания уже защищены мьютексом, поллер умеет просыпаться извне — но
   общий AOF, общие счётчики и пробуждение чужих циклов ещё не сделаны.
2. **I/O-потоки**: долгая команда (например, `KEYS` по большому keyspace)
   сейчас держит весь цикл — как в Redis, но там есть I/O-потоки.
3. **M22–M23** (репликация) — следующие содержательные вехи.

## 4. Известные ограничения (зафиксированы намеренно)

| Что | Почему | Где смотреть |
|---|---|---|
| `DUMP`/`RESTORE` — свой формат payload'а | настоящий Redis такой payload не восстановит | `internal/persist/dump.go` |

| Приблизительная обрезка (`XTRIM … ~`) удаляет целыми блоками по 100 записей | в Redis блоки — это узлы rax (до 100 записей и 4 КБ), у нас единого узла нет | `internal/store/stream.go` (`approximateCut`) |
| `XINFO STREAM`: `radix-tree-keys`/`radix-tree-nodes` — приблизительные | эти поля описывают внутреннее устройство Redis (radix-дерево); у нас поток — это один срез | `internal/server/commands_stream_group.go` (`radixTreeKeys`) |
| Нет команд с TTL полей хэша (`HEXPIRE`/`HTTL`/`HSETEX`) | требуют поддержки TTL полей в RDB, иначе данные терялись бы при сохранении | `docs/roadmap-m0-plus.md` (M11) |
| `SORT` без `BY`/`GET` требует числовых элементов | как в Redis: иначе `ERR One or more scores can't be converted into double` | `internal/server/commands_keys.go` |
| `HSCAN`/`SSCAN`/`ZSCAN` — курсор = индекс в отсортированный снимок коллекции | снимок строится один раз на обход (P5), а не на каждый вызов; при изменении коллекции снимок строится заново, и элементы, добавленные или удалённые посередине обхода, могут не попасть в ответ — как и в Redis | `internal/server/commands_scan.go`, `internal/store/scan.go` |
| `COUNT` в сканах — строгий лимит (в Redis — подсказка) | границы батчей у разных реализаций разные, поэтому харнесс сравнивает весь обход | `testdata/compat/scan.txt` |
| В режиме event loop (он по умолчанию) одна долгая команда держит все соединения | как в Redis: там цикл тоже один, но есть I/O-потоки; откат — `--io-mode=goroutine` | `internal/server/loop.go` |
| Обрыв соединения заблокированного клиента замечается только по таймауту | в Redis помогает `CLIENT KILL` | `internal/server/blocking.go` |
| `CLIENT KILL` убивает соединение, `CLIENT UNBLOCK` — разблокированного клиента; `CLIENT NO-EVICT`/`NO-TOUCH` — без эффекта | `CLIENT NO-EVICT`/`NO-TOUCH` в Redis меняют поведение клиента, у нас это только ответ | `internal/server/commands_admin.go` |
| Нет `EVAL`/`FUNCTION`, кластера, `ACL`, Geo, HyperLogLog, битовых операций | отложены | `ROADMAP.md` |

## 5. Тонкости Redis, которые пришлось повторить (неочевидные!)

Это места, где документация Redis вводит в заблуждение или не покрывает
поведение. Харнесс их уже проверяет — при добавлении новых команд смотри
сюда, а не в доки Redis.

- `LINSERT` возвращает **-1**, когда pivot не найден, и **0**, когда нет ключа
  (в доках наоборот).
- `HGETDEL` (Redis 8) возвращает **массив удалённых значений**, а не число;
  для отсутствующего поля — `[nil]`. Синтаксис: `HGETDEL key FIELDS n field…`.
- `SORT` без `ALPHA` требует, чтобы все элементы были числами (иначе ошибка);
  с `BY` нечисловой вес считается **нулём**; `GET` подставляет значения
  найденных ключей (нет ключа → `nil`).
- `LPOS`: `COUNT` не может быть отрицательным; `MAXLEN` ограничивает **окно
  просмотра**, а не число ответов; при заданном `COUNT` ответ — массив, без
  него — одно число.
- `ZRANGE … REV` без `BYSCORE`/`BYLEX` применяет индексы к **обратному**
  порядку множества; с `BYSCORE`/`BYLEX` границы **меняются местами**.
- `TTL` округляется до **ближайшей секунды** (`(ms+500)/1000`).
- `BLPOP`/`BRPOP` → `[key, value]`, `BZPOPMIN`/`BZPOPMAX` → `[key, member, score]`,
  по таймауту — null-массив.
- `INCRBYFLOAT` печатает **17 значащих цифр** без экспоненты
  (`10.5 + 0.1` → `10.59999999999999964`), а `ZSCORE` — кратчайшую форму
  (`10.6`).
- Формы ответов RESP3: `ZRANGE WITHSCORES` → массив пар `[member, double]`
  (не плоский массив!), `CONFIG GET`/`HGETALL` → карта, `SMEMBERS` →
  множество, `SDIFF`/`SINTER`/`SUNION` → множество, Pub/Sub → push-кадры.
- `DUMP`/`RESTORE` у настоящего Redis: `RESTORE` без `REPLACE` на занятый
  ключ → `BUSYKEY Target key name already exists.`
- **Streams** (Redis 8.2):
  - идентификатор записи — `ms-seq`; `XADD` с явным `0-0` → `ERR The ID
    specified in XADD must be greater than 0-0`; идентификатор должен быть
    строго больше верхнего элемента, иначе `ERR The ID specified in XADD is
    equal or smaller than the target stream top item`;
  - `XADD key 5` (без `-seq`) допустим — это `5-0`; `XADD key 5-*` — авто-seq;
    `ms-*` с миллисекундой **меньше** последней записи → ошибка;
  - `XSETID` сравнивается с последней **записью**, а не с `lastID` (который
    сам `XSETID` и поднимает): `XSETID s 100-0` потом `XSETID s 50-0` — ошибка
    только если 50-0 меньше верхней записи;
  - `XRANGE`/`XREVRANGE` отвечают массивом пар `[id, [f, v, f, v …]]`;
    эксклюзивная граница — префикс `(`; `COUNT 0` → **null-массив**;
  - маркеры `~`/`=` у `MAXLEN`/`MINID` распознаются, только если после них
    есть значение; `LIMIT` без `~` → `ERR syntax error, LIMIT cannot be used
    without the special ~ option`;
  - приблизительная обрезка (`~`) в Redis удаляет целые узлы rax, поэтому её
    результат зависит от раскладки — у нас тоже (блоки по 100 записей);
  - в AOF попадает **фактический** идентификатор записи, а `~` переписывается
    в `=` с получившейся длиной — иначе реплей дал бы другой поток.
- **Группы потребителей** (Redis 8.2):
  - `XREADGROUP … >` отдаёт записи потока **после** идентификатора группы и
    кладёт их в список неподтверждённых; `XREADGROUP … <id>` отдаёт
    **собственные** неподтверждённые записи потребителя (и увеличивает число
    доставок), а не записи потока;
  - `XACK` на несуществующей группе/ключе → `0` (не ошибка), а `XPENDING`,
    `XAUTOCLAIM`, `XINFO CONSUMERS` → ошибка `NOGROUP`;
  - `XINFO GROUPS`: `entries-read` и `lag` — **null**, если счётчик группы
    неизвестен (группа создана без `ENTRIESREAD` и ещё ничего не читала);
  - в сводке `XPENDING` число неподтверждённых записей потребителя — **bulk
    строка** (в Redis `addReplyBulkLongLong`), а не целое число: харнесс
    сравнивает типы значений;
  - `XINFO STREAM` без `FULL` — 10 пар, с `FULL` — 9 пар (поля потока, его
    записи и группы); поля `radix-tree-keys`/`radix-tree-nodes` описывают
    внутреннее устройство Redis, у нас они приблизительные (1 и 2 для
    небольших потоков — совпадают);
  - `XGROUP HELP` и `XINFO HELP` отвечают **массивом** строк (по строке на
    элемент), а не одной строкой;
  - `XGROUP` с несуществующим ключом → «ERR The XGROUP subcommand requires
    the key to exist…», а с несуществующей группой → `NOGROUP`;
  - приблизительная обрезка `XTRIM … ~` в Redis удаляет целые узлы rax, поэтому
    её результат зависит от раскладки — у нас тоже (блоки по 100 записей).

## 6. Как проверять

```bash
go build ./... && go vet ./... && gofmt -l .    # должно быть чисто
go test -race ./...                              # зелёный
go test -race -count=3 ./internal/...            # стабильность

# сверка с настоящим Redis 8.2 (поднимает оба сервера)
scripts/compat-check.sh

# только наша реализация
go run ./cmd/redis-server --port 6379

# производительность
redis-benchmark -p 6379 -t get,set -n 100000 -c 50 -P 50
```

Правила оформления кода (по образцу уже сделанного):
- Хранилище: доступ на чтение — под `RLock`, на запись — под `Lock`;
  `Entry.lastAccess` — `atomic.Int64`; чтение коллекции выполняется **под**
  блокировкой (иначе гонка «concurrent map read and map write»).
- Новая команда: регистрация в `internal/server/commands.go` через
  `reg`/`regW`/`regWG`/`regWS`/`regWSG` (арность + флаги write/aofSelf/memAdd)
  и **обязательно** обновление списков в `internal/server/registry_test.go` —
  тест инвариантов реестра сам поймает забытую write-команду.
- AOF: новая пишущая команда добавляется в `aofWriteCommands` (через реестр)
  и в разбор `internal/persist/aof.go` (`applyAOFCommand`).
- Разбор аргументов команды, который нужен и серверу, и реплею AOF, живёт в
  `internal/store` (как `ParseStreamAddArgs`/`ParseStreamTrimArgs`): пакет
  `persist` не может импортировать `server` (цикл), а дублировать разбор
  опасно.
- Сценарий сверки: `testdata/compat/<family>.txt`, новые команды — туда же.
  Проверять поведение лучше живым `redis-cli` против локального
  `redis-server 8.2`: в zsh `~` и `*` expanding — кавычить (`"~"`, `"*"`).

Порядок слияния стека MR (как делали 22.10, чтобы не наступить на те же грабли):
- GitHub сливает PR **в его базовую ветку**, а не в `main` — после слияния
  нижнего MR стек схлопывается в боковые ветки, а `main` больше ничего
  не получает;
- поэтому MR ниже по стеку перед слиянием переставляют на `main`:
  `gh pr edit <n> --base main`, затем `gh pr ready <n>` (draft слить нельзя)
  и `gh pr merge <n> --merge` — merge-коммитом, снизу вверх;
- содержимое уже слитых «в бок» MR (`!2`/`!3` в тот раз) доезжает до `main`
  через следующий MR, чей head их уже включает;
- ветки вех удалять **только после** последнего слияния (пока база следующего
  MR живёт на ветке, удалять её нельзя) — локально и на GitHub, затем
  `git fetch --prune`;
- после слияния — полный прогон на обновлённом `main` (см. §6 выше) и
  `COMMAND COUNT` через `redis-cli` как быстрая проверка покрытия.
